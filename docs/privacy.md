<a id="english"></a>
## English

Protecting patient confidentiality and medical information is paramount. This document details how `dicom-organizer` handles patient identifiers, what data is modified or retained across different modes, and the essential steps required before sharing datasets.

### 1. Fundamental Principles: What `dicom-organizer` Does NOT Do

> [!CAUTION]
> **`dicom-organizer` is NOT an anonymization or de-identification tool.**
> - **DICOM binary files are never modified**: When organizing files (copy, link, or move), the DICOM binary content and internal metadata headers are preserved bit-for-bit. Patient names, IDs, dates of birth, and study UIDs remain embedded in all DICOM files.
> - **Metadata pseudonymization only**: The `--patient-mode` option alters only the text metadata CSVs and JSON reports generated by the tool, not the DICOM files themselves.

### 2. Patient Privacy Modes (`--patient-mode`)

The `--patient-mode` setting controls how direct patient identifiers are represented in CSV metadata tables:

| Mode | `PatientName` in CSV | `PatientID` in CSV | `PatientNameHash` in CSV | `PatientIDHash` in CSV | Intended Use Case |
|---|---|---|---|---|---|
| **`keep`** (default) | Original plaintext (e.g. `SAMPLE^DELTA`) | Original plaintext | 16-char SHA-256 digest (e.g. `5ce3e247d5cac86d`) | 16-char SHA-256 digest (e.g. `5ce3e247d5cac86d`) | Secure internal clinical research where verified patient identification is required. |
| **`hash`** | `sha256:` + 16-char digest (e.g. `sha256:5ce3e247d5cac86d`) | `sha256:` + 16-char digest | 16-char SHA-256 digest | 16-char SHA-256 digest | Internal team analysis where tracking repeat visits across sessions is needed without plaintext names. |
| **`drop`** | `N/A` | `N/A` | `N/A` | `N/A` | Preparing metadata tables for broader sharing or auditing where patient identifiers are strictly excluded. |

### 3. What Changes and What Remains Across Output Files

Understanding retained data across output files is essential for institutional compliance:

| Output File | In `keep` Mode | In `hash` Mode | In `drop` Mode | Crucial Retained Identifiers |
|---|---|---|---|---|
| **Organized DICOM Files** (`*.dcm`) | Unmodified | Unmodified | Unmodified | Full DICOM headers (PatientName, PatientID, dates, UIDs, private tags). |
| `all_series_summary.csv` | Plaintext names & IDs, SHA-256 digests | `sha256:`-prefixed names & IDs, SHA-256 digests | `N/A` for names, IDs, and hashes | StudyDate, StudyTime, AcquisitionDate, Manufacturer, ManufacturerModelName, SeriesDescription, ProtocolName, UIDs. |
| `all_dicom_parameters.csv` (list-only mode) | Plaintext names & IDs, SHA-256 digests | `sha256:`-prefixed names & IDs, SHA-256 digests | `N/A` for names, IDs, and hashes | StudyDate, StudyTime, AcquisitionDate, Manufacturer, ManufacturerModelName, SourceFileName, geometric coordinates, UIDs. |
| `dicom_parameters.csv` (per study folder) | Plaintext names & IDs, SHA-256 digests | `sha256:`-prefixed names & IDs, SHA-256 digests | `N/A` for names, IDs, and hashes | StudyDate, StudyTime, AcquisitionDate, Manufacturer, ManufacturerModelName, SourceFileName, OrganizedFileName, geometric coordinates, UIDs. |
| `series_summary.csv` (per study folder) | Plaintext names & IDs, SHA-256 digests | `sha256:`-prefixed names & IDs, SHA-256 digests | `N/A` for names, IDs, and hashes | StudyDate, StudyTime, AcquisitionDate, Manufacturer, ManufacturerModelName, SeriesDescription, ProtocolName, UIDs. |
| `file_report.csv` | No name/ID columns | No name/ID columns | No name/ID columns | 11 columns: `SourceFileName`, `Status`, `Reason`, `Detail`, `OrganizedFileName`, `DuplicateOf`, `SOPInstanceUID`, `SeriesUID`, `Modality`, `SizeBytes`, `SHA256`. |
| `organize_summary.json` | Run options & counts | Run options & counts | Run options & counts | Absolute paths of input and output folders (`input_root`, `output_root`), run options, skip reason tallies. |

> [!WARNING]
> **Source Directory and File Names**: `SourceFileName` in `file_report.csv`, `dicom_parameters.csv`, and `all_dicom_parameters.csv` reflects the original relative path. If your clinical export or folder names contain patient names or patient IDs (e.g., `Smith_John_12345/`), these will be visible in the reports! Note that `SourceFileName` is not included in `all_series_summary.csv`.
>
> **Patient Identifiers in Folder Names with `--layout patient-study`**: When `--layout patient-study` is used, the patient identifier is included in folder names. Under `keep`, the original PatientID is used (sanitized to safe characters). Under `hash` and `drop`, a pseudonymized key formatted as `P-` followed by a 12-character SHA-256 digest is used.
>
> **Custom Tags via `--dicom-tag`**: If you use `--dicom-tag` to extract custom DICOM attributes into CSVs, any specified tags—including direct patient identifiers such as PatientBirthDate—will be written verbatim into metadata CSV tables regardless of `--patient-mode`.
>
> **Absolute Paths in `organize_summary.json`**: The summary JSON records the absolute paths of both the input and output directories on your system.

### 4. Hash Mode is Pseudonymization, Not Anonymization

The `hash` mode generates a 16-character SHA-256 hexadecimal hash (`hashlib.sha256(value.encode()).hexdigest()[:16]`).
- **Vulnerability to Dictionary Attacks**: Because patient IDs within a clinic or hospital often follow predictable numeric sequences (e.g., 7 or 8 digits), an attacker can easily pre-compute SHA-256 digests and reconstruct the original patient identity.
- Therefore, CSVs generated with `--patient-mode hash` must **never** be posted to public repositories or shared outside the secure research environment.

### 5. Proper De-identification via DICOM PS3.15 Annex E

When exporting imaging data for public release or inter-institutional multi-center trials:
1. Use a dedicated, validated DICOM de-identification pipeline compliant with **DICOM PS3.15 Annex E** (Attribute Confidentiality Profiles, such as the *Basic Application Level Confidentiality Profile*).
2. Cleanse patient names, dates, institutional addresses, accession numbers, and UIDs directly within the DICOM binary datasets.
3. Verify that burned-in pixel annotations or ultrasound graphics containing patient text are purged.
4. Only after dedicated de-identification should files be shared externally.

<a id="japanese"></a>
## 日本語

医療情報・患者プライバシーの保護は、画像研究における最優先事項です。本文書では、`dicom-organizer` における患者情報の取り扱い、各出力ファイルに変更される項目・残る項目、および外部共有前の必須手順を明記します。

### 1. 基本原則: 本ツールが「行わないこと」

> [!CAUTION]
> **`dicom-organizer` は DICOM の匿名化・脱特定化ツールではありません。**
> - **DICOM バイナリ自体は一切変更されません**: ファイル整理（コピー、移動、シンボリックリンク作成）を実行しても、DICOM ファイル内部のヘッダーや画像データは 1 バイトも書き換えられません。患者氏名、患者 ID、生年月日、検査 UID 等は DICOM ファイル内にそのまま残ります。
> - **変更されるのは生成される CSV・レポートのみ**: `--patient-mode` オプションは、ツールが新規作成する CSV 表や JSON レポート内のテキスト出力を制御するものであり、DICOM 画像ファイル本体には影響しません。

### 2. プライバシーモードの選択 (`--patient-mode`)

CSV メタデータ表における直接的な患者識別子の扱いを制御します:

| モード | CSV の `PatientName` | CSV の `PatientID` | CSV の `PatientNameHash` | CSV の `PatientIDHash` | 想定される用途 |
|---|---|---|---|---|---|
| **`keep`**（既定値） | 元の平文氏名（例: `SAMPLE^DELTA`） | 元の平文 ID | SHA-256 先頭 16 文字のハッシュ値（例: `5ce3e247d5cac86d`） | SHA-256 先頭 16 文字のハッシュ値（例: `5ce3e247d5cac86d`） | 院内や施設内の保護された環境で、患者の突合が必要な研究。 |
| **`hash`** | `sha256:` + 先頭 16 文字（例: `sha256:5ce3e247d5cac86d`） | `sha256:` + 先頭 16 文字 | SHA-256 先頭 16 文字のハッシュ値 | SHA-256 先頭 16 文字のハッシュ値 | 院内研究チーム内で、平文氏名を隠蔽しつつ同一患者の追跡を行う場合。 |
| **`drop`** | `N/A` | `N/A` | `N/A` | `N/A` | 患者識別子を完全に排除して撮像条件表を共有・分析する場合。 |

### 3. 各出力ファイルに変更されるもの・残るもの

情報漏えいを防ぐため、各ファイルに出力される内容を把握してください:

| 出力ファイル | `keep` モード | `hash` モード | `drop` モード | 残存する重要な識別情報 |
|---|---|---|---|---|
| **整理後 DICOM ファイル** (`*.dcm`) | 変更なし | 変更なし | 変更なし | DICOM ヘッダー全体（氏名、ID、日付、UID、private タグ等）。 |
| `all_series_summary.csv` | 平文氏名・ID、SHA-256 ハッシュ | `sha256:` 付与の氏名・ID、SHA-256 ハッシュ | 氏名・ID・ハッシュとも `N/A` | 検査日（`StudyDate`）、時刻（`StudyTime`、`AcquisitionDate` 等）、装置名（`Manufacturer`、`ManufacturerModelName`）、系列名（`SeriesDescription`）、プロトコル名（`ProtocolName`）、各 UID。 |
| `all_dicom_parameters.csv`（一覧のみモード） | 平文氏名・ID、SHA-256 ハッシュ | `sha256:` 付与の氏名・ID、SHA-256 ハッシュ | 氏名・ID・ハッシュとも `N/A` | 検査日、時刻、装置名、`SourceFileName`、幾何座標、各 UID。 |
| `dicom_parameters.csv`（検査フォルダごと） | 平文氏名・ID、SHA-256 ハッシュ | `sha256:` 付与の氏名・ID、SHA-256 ハッシュ | 氏名・ID・ハッシュとも `N/A` | 検査日、時刻、装置名、`SourceFileName`、`OrganizedFileName`、幾何座標、各 UID。 |
| `series_summary.csv`（検査フォルダごと） | 平文氏名・ID、SHA-256 ハッシュ | `sha256:` 付与の氏名・ID、SHA-256 ハッシュ | 氏名・ID・ハッシュとも `N/A` | 検査日、時刻、装置名、系列名、プロトコル名、各 UID。 |
| `file_report.csv` | 氏名・ID 列なし | 氏名・ID 列なし | 氏名・ID 列なし | 次の 11 列が出力されます: `SourceFileName`、`Status`、`Reason`、`Detail`、`OrganizedFileName`、`DuplicateOf`、`SOPInstanceUID`、`SeriesUID`、`Modality`、`SizeBytes`、`SHA256`。 |
| `organize_summary.json` | 実行オプションと件数 | 実行オプションと件数 | 実行オプションと件数 | 入出力フォルダの絶対パス（`input_root`、`output_root`）、実行オプション、スキップ理由件数。 |

> [!WARNING]
> **元のファイル名やフォルダ名（`SourceFileName`）への注意**:
> `file_report.csv`、`dicom_parameters.csv`、`all_dicom_parameters.csv` に出力される `SourceFileName` は、入力時の相対パスをそのまま記録します。元のフォルダ名やファイル名に患者氏名や患者 ID が含まれている場合（例: `Yamada_Taro_12345/`）、レポート内にそのまま出力されます。なお、`all_series_summary.csv` には `SourceFileName` 列はありません。
>
> **`--layout patient-study` 使用時のフォルダ名**: `--layout patient-study` を使用すると、フォルダ名に患者情報が出力されます。`keep` では患者 ID そのもの（安全な文字に変換）、`hash` および `drop` では `P-` + 12 桁の SHA-256 ハッシュが出力されます。
>
> **`--dicom-tag` による任意のタグの追加**: `--dicom-tag` を使用して追加した任意のタグ（例: 生年月日 `PatientBirthDate` など直接識別子）は、`--patient-mode` の指定にかかわらず平文のまま CSV に出力されます。
>
> **`organize_summary.json` に記録される絶対パス**: `organize_summary.json` には、実行時の入力フォルダおよび出力フォルダのローカル絶対パスがそのまま記録されます。

### 4. ハッシュ化は「仮名化」であり「匿名化」ではありません

`hash` モードは SHA-256 ハッシュの先頭 16 文字（`hashlib.sha256(value.encode()).hexdigest()[:16]`）を出力します。
- **辞書攻撃に対する脆弱性**: 病院の患者 ID は桁数や規則が決まっていることが多く、全パターンのハッシュ値を事前に計算することで元の患者 ID を特定（復元）できる危険があります。
- したがって、`--patient-mode hash` で作成した CSV であっても、オープンな GitHub リポジトリ等の外部に公開してはなりません。

### 5. DICOM PS3.15 Annex E に準拠した専門ツールによる匿名化

共同研究先へのデータ提供や学会発表など、データを外部環境へ持ち出す場合:
1. **DICOM PS3.15 Annex E**（Attribute Confidentiality Profiles）に準拠した、施設で承認された専門の DICOM 匿名化ツールを使用してください。
2. DICOM バイナリ内部の氏名、ID、日付、生年月日、施設情報、UID を適切に削除または置換してください。
3. 超音波画像や二次捕獲画像など、画像ピクセル内に患者情報が焼き付けられていないか（burned-in annotation）を確認してください。
4. 適切な匿名化処理が完了したことを確認したうえで外部に提供してください。
