# 利用者調査計画書（ユーザーリサーチ計画）

本文書は、`dicom-organizer` が臨床現場および研究現場において「手元の DICOM を整理し、撮像条件を確かめ、次の作業に渡すときの定番ツール」として定着するために実施する利用者調査（インタビューおよび初回操作観察）の計画書です。

---

## 1. 調査の目的と検証する仮説

本調査では、開発者の想定と現場の実態との乖離を特定するため、以下の 4 つの**仮説**を検証します:

1. **初期利用の仮説**:
   利用者は「外付けメディアやダウンロードした散乱フォルダの全容が分からない」という強い課題を抱えており、「一覧のみモード」または「整理モード」によって数分以内に最初の安心感（成功体験）を得られる。
2. **初回操作のつまずき仮説**:
   利用者が最初に操作を止めてしまうボトルネックは、「未署名アプリの初回起動セキュリティ警告」または「プライバシー設定（患者情報をどう扱うべきか）」の判断にある。
3. **次の作業への引き渡し仮説**:
   整理後の主たる用途は、「Excel でのプロトコル比較確認」または「3D Slicer / dcm2niix への入力」であり、生成される CSV の列構成がそのまま次の作業の入力として機能する。
4. **繰り返しの仕事と定着の仮説**:
   1 回きりの利用で終わらず、新しい検査データが届くたびに定期的に利用されるための鍵は、「設定の記憶」と「中断後の安全な再開（`--if-exists skip`）」にある。

---

## 2. 調査対象者と募集方針

実務で DICOM データを日常的に扱う以下の役割から、各 3〜5 名を対象とします:
- **診療放射線技師**: MRI / CT のプロトコル管理・品質管理（QA）を担当する技師。
- **医用画像研究者・医師**: 過去の症例画像から特定のシーケンスを抽出して解析する研究者。
- **画像解析エンジニア**: Python 等で機械学習や画像処理パイプラインを構築する技術者。

---

## 3. 聞き取り（インタビュー）の質問項目

1. **現在の仕事の流れ**:
   - 普段、DICOM データを受け取ったとき、最初にどのような手順で中身を確認・整理していますか？
   - その作業で最も時間のかかっている部分や、ストレスを感じる点は何ですか？
2. **ツールの発見と導入**:
   - このツールをどこで知りましたか？職場で新しいツールを試す際の障壁は何ですか？
3. **整理後の作業**:
   - 整理されたフォルダや CSV 表を使って、次にどんなソフトや作業へデータを渡しますか？
4. **同僚への推薦**:
   - どのような機能や安心感があれば、同じ研究室や部署の同僚にこのツールを勧めたい（**推薦**したい）と思いますか？

---

## 4. 初回利用の行動観察（ユーザビリティ観察）手順

事前の口頭説明を一切行わず、以下の標準課題を自力で達成できるかを観察・記録します:

1. **観察の課題**:
   - 「配布された zip（または Python 環境）からツールを起動し、用意されたサンプルデータを用いて撮像パラメータの一覧表を作成してください」
2. **記録する指標**:
   - **所要時間**: アプリ起動から CSV を開いて確認するまでの所要秒数。
   - **説明なし達成率**: 調査員からの助言なしで課題を完遂できたか。
   - **迷い・停止の箇所**: マウスの停止、エラー表示、画面の行き来が発生したポイント。
3. **成功条件**:
   - 最初の 3 分以内に、パラメータ一覧表（CSV または GUI プレビュー）の確認に到達できること。

## 5. 患者情報（個人情報）保護の厳守方針

調査における**患者情報**の取り扱いには細心の注意を払います:
- **実データの禁止**: 利用者調査において、実際の臨床患者データや施設の機密データを画面に表示させたり、ログに記録したりすることを固く禁止します。
- **合成データの使用**: 観察セッションでは、リポジトリに内蔵されている合成サンプルデータ（`create_sample_dataset` 由来）のみを使用します。
- **記録の匿名化**: 参加者の所属や氏名は記号化（例: 技師 A、研究者 B）して記録します。

## 6. 到達指標の段階（ファネル）と計測方法

プライバシーを尊重し、本ソフトウェアには一切のテレメトリ（利用計測通信）を組み込みません。その代わり、公開指標と聞き取りによって以下の段階を測定します:

| 段階 | 定義 | 主な測定方法・指標 |
|---|---|---|
| **発見** | ツールの存在を知る | GitHub リポジトリ訪問数、Releases 閲覧数、学会・勉強会での紹介 |
| **導入** | 手元環境へインストールする | PyPI ダウンロード数、GitHub Releases の zip ダウンロード数 |
| **初回利用** | 最初の整理または一覧作成を完了 | 観察セッションでの説明なし完了率、初期の不具合報告の有無 |
| **継続** | 複数の検査・研究で繰り返し使う | 定期的なバージョン追従、Discussions での継続的な質問 |
| **推薦** | 同僚やチームに広める | 勉強会での言及、施設マニュアルへの記載、同僚への紹介 |
| **定着** | 組織の標準手順書に組み込まれる | 共同研究のデータ受け入れ基準や標準手順書（SOP）への採択 |

---

## 7. 結果から次に作る機能を決める判断基準

調査で得られた要望や観察結果は、以下の客観的基準に基づいて優先度を判定します:

- **最優先（直ちに対処）**: 初回利用で作業が停止する操作上の混乱（迷いの観察）、データの安全や患者プライバシーに関する誤解を招く表示。
- **高優先（次のマイナー版で実装）**: 複数メーカー間での撮像条件比較で頻出する欠損パラメータの救済、次のツール（3D Slicer, dcm2niix 等）への連携上の不都合。
- **見送り（対象外）**: ビューア機能や PACS 通信機能など、本ツールの非目標（他ツールに委ねる領域）に属する要望。
